# 설계결정 0001 — 클라우드 계약은 엣지 회수 기전에 중립이다

- **상태**: 채택 (2026-09-21)
- **영향 범위**: `schema/edge_contract.json` · 판정 레코드 스키마 · 보고서 §0 · §4-7

---

## 1. 맥락 — 엣지에 두 개의 구현이 존재한다

같은 "슬랙 회수"라는 이름 아래 **서로 다른 두 기전**이 실재한다.

| | **선점 + 재개** | **승인 제어 + 완주** |
|---|---|---|
| 위치 | `NeedSlack/07_RTL/` | `NeedSlack/Teammate/slack_reclaim_zybo_v5/` (보드 반입본) |
| 상태 보존 | `stage2_scorer.v` `partial_bank[]` · `preempt_pend[]` · `resume_cnt` | **없음** (`preempt`/`resume`/`partial_bank` 0건) |
| 진입 판정 | `grant = slack > Ĉ_bg + L_pre + L_mem + MARGIN` | `cost ≤ close_tick − elapsed` |
| 실행 중 | **선점 → 부분합 보존 → 재개** | 완주만. 초과 시 `fault[2]`/`fault[3]` |
| 슬랙 회수 | 매 클록 재판정 | **진입 시 1회** (`dynamic_mode=1` 팔 존재) |
| 실측 | `.sim/rt.log` DYN `resume_cnt = 4` · STA `= 0` | `docs/BOARD_50MS_RESULTS.md` 회수 2,911,612 tick |

두 용어는 같은 것이 아니다. **비선점**은 실행 *중*의 성질("시작한 일을 뺏지 않는다"),
**승인 제어**는 *진입* 시점의 정책("못 끝낼 일을 시작하지 않는다")이다. 보드는 둘 다이며,
그것은 우연이 아니다 — **비선점이기 때문에 승인 제어가 필요하다.** 실행 중에 뺏을 수
없으면 데드라인을 지킬 지렛대가 진입 판정뿐이다.

축은 "동적 vs 정적"이 아니라 **회수 결정의 시간 해상도**다:

| | 창을 언제 여나 | 실행 중 재판정 |
|---|---|---|
| 정적 예약 | 고정 시점 (`elapsed ≥ budget`) | 없음 |
| 보드 `dynamic_mode=1` | 전경 종료 즉시 (실제 슬랙) | **없음** |
| `07_RTL` | 전경 종료 즉시 | **매 클록** |

---

## 2. 결정

> **클라우드가 소비하는 계약은 회수 기전에 중립이다.** 회수 기전은 계약의 *값*이 아니라
> 계약을 *강제하는 방법*이며, 클라우드는 값에만 의존한다.
>
> 단, **어느 기전이 그 판정을 만들었는지는 판정 레코드에 기록한다.**

---

## 3. 근거

### 3-1. 대역·큐·지연 계약은 영향받지 않는다 — 식에 `g`가 없다

```
업로드량 = rate · f_cand · S          ← g 가 들어가지 않는다
```

(`NeedSlack/01_문서/갈래A_전환.md §6-5`) `g`는 회수 기전이 바꾸는 양이고 `rate`는 선별 정책이
정하는 양이다. 회수 기전은 **같은 10%를 더 잘 고르게** 만들 뿐 업로드량을 바꾸지 않는다.

따라서 업링크 수요 2.312 Mbps · `rate_sustain` 0.0433 · `δ_max` 0.4325 ·
`L_max` 13.62 h · `Q_min` 6.13 GB · 드롭 정책 — **전부 기전과 무관하다.**
보고서 §1~§3(수집·백엔드·MLOps)은 어느 구현에서도 그대로 성립한다.

### 3-2. 판정 지연 상한은 같고, 강제 기전이 다르다

| | 상한 | 강제 방법 |
|---|---|---|
| 선점형 | ≤ 50 ms | `frame_start`가 채점 상태를 리셋 → 프레임을 가로질러 살아남지 못함 |
| 승인제어형 | ≤ 50 ms | `close_tick = period − margin` 밖으로 나갈 일을 시작하지 않음 |

상한이 같으므로 클라우드 상태기계(`PENDING → UPLOADED`)는 그대로다.
보고서 §0 계약표가 기전을 단일 구현으로 못박지 않는 이유가 이것이다.

### 3-3. ⚠ 품질 논거는 영향받는다 — 선점 입도에 걸려 있다

`갈래A_전환.md §2-5` (선언 운용점 14 GMAC/s · `C_TILE` 11.71 ms):

| 입도 `k` | 깊이 DYN | 깊이 STA | Δ깊이 |
|---|---|---|---|
| **1** (타일 경계) | 0.85 | 1.00 | **−15%** |
| 4 (`k*` 손익분기) | 1.79 | 1.75 | +2% |
| **∞** (헤드라인 근거) | **1.85** | **1.00** | **+85%** |

헤드라인 **+85%는 `L_pre ≈ 0`에서 측정**됐다 — `y4_select_axis2.py:136`의 `n_tiles()`가
창에서 `L_pre`를 빼지 않는다(`§2-6`). 입도가 거칠어지면 이득이 줄고 `k = 1`에서는
**부호가 뒤집힌다.**

입도를 잘게 하는 것이 공짜가 아니라는 점이 이 결정의 배경 제약이다:

```
k = 1  체크포인트 132 bit      → FF +148 · BRAM +0
k > 1  활성화맵 262,144 B      → 57 RAMB36 = xc7z020 BRAM 의 +40.7%p
```

**보드가 `k = 1` 쪽에 있는 것은 선택이 아니라 디바이스 제약이다.**

### 3-4. 승인제어 운용점은 미측정 — 그리고 **이번 범위에서 측정하지 않는다**

`§2-5` 표의 `k = 1` 행은 `L_pre = C_TILE`을 창에서 **빼고** 계산한다. 승인제어는
선점 대기를 발생시키지 않으므로 `L_pre`를 내지 않고, 대신 승인이 보수적이다.

```
DYN 행 (측정됨)   floor( max(0, win_dyn − L_pre) / C_G )    동적 창 · L_pre 지불
STA 행 (측정됨)   floor(          win_sta        / C_G )    고정 창 · L_pre 없음
승인제어 (미측정) floor(          win_dyn        / C_TILE )  동적 창 · L_pre 없음
```

부분 근거는 있다 — `BOARD_50MS_RESULTS.md`가 동적 팔에서 회수 구간 service 2,911,612 tick,
C 완료→S 시작 간격 **2 tick**을 기록했다. 다만 6프레임 candidate-limited 설정이라
완료 job 이 23 대 23 으로 같고, **깊이 차이가 나올 수 없는 조건**이다.

> **결정: 측정하지 않는다.**
> 스윕 결과가 어떤 값이든 §2 의 결정이 바뀌지 않는다. 결정을 바꾸지 않는 측정은
> 이번 범위의 측정이 아니다. 클라우드 데모는 `STA_B`·`DYN_B` 두 팔만 통과시키며
> (보고서 §5-3), 보드 변형은 파이프라인에 들어오지 않는다.

## 4. 귀결 — 판정 레코드에 기전을 기록한다

함대에 두 구현이 섞이면 **선별 품질이 다른 두 모집단이 한 풀에 섞인다.** 재학습 mAP 가
움직였을 때 원인이 데이터인지 구현인지 분리할 수 없다. `profile_sha` 를 넣은 것과 같은 논리다.

```jsonc
// DynamoDB ns-curation-index 아이템
"reclaim_mode": "preempt_resume",   // | "admission_nonpreempt" | "static_reserve"
"granule_k":    1,                  // 선점 입도. 승인제어는 1 고정
"l_pre_cyc":    0,                  // 이 프레임이 실제로 지불한 선점 대기
"tiles_scored": 2,                  // 승인제어는 항상 정수. 선점형은 부분 타일 가능
"resume_cnt":   0,                  // 선점형 전용. 승인제어는 0 고정
"rtl_build":    "zybo_v5"           // 비트스트림 식별자
```

⚠ `tiles_scored` 의 **의미가 기전마다 다르다.** 승인제어에서는 완주 타일 수라 항상
정수지만, 선점형에서는 `partial_bank` 에 부분합만 쌓인 타일이 존재할 수 있다.
집계 시 두 모집단을 같은 히스토그램에 넣지 않는다.

`dataset_frame` 에도 `reclaim_mode` 를 실어 학습/평가 스플릿이 기전을 가로질러 섞이지
않게 한다. 섞인 데이터셋으로 낸 mAP 는 어느 기전의 성능도 아니다.
