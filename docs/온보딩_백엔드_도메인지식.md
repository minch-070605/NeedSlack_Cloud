## 0. 먼저 — 현황 진단 (이 브리핑의 전제)

지시서는 "현재 폴더 내의 **서버 구성 파일, API 명세, 데이터베이스 스키마 정의서**를 읽고"
브리핑하라고 했습니다. 실제로 읽은 결과를 그대로 보고합니다.

```
needslack-cloud/
├ docs/개발기록.md                             설계 문서
├ docs/ 분석보고서_Edge투Cloud아키텍처.md    설계 문서
│      설계결정-0001-엣지-회수기전-중립성.md      설계 결정 기록
│      build_artifact.py                   문서 렌더러 (서버 코드 아님)
├ schema/ edge_contract.json               엣지 계약 스냅샷 (데이터, 스키마 아님)
│         gen_edge_contract.py             위 파일 생성기 (서버 코드 아님)
├ infra/        (비어 있음)
├ edge-agent/   (비어 있음)
└ pipelines/    (비어 있음)
```

| 지시서가 전제한 것 | 실제 |
|---|---|
| 서버 구성 파일 | ❌ **없음** (`Dockerfile`·`*.yaml`·`*.tf`·`requirements.txt` 전부 0건) |
| API 명세 | ❌ **없음** (OpenAPI/Swagger 파일 0건). 리소스 초안은 보고서 §2-2 본문에만 존재 |
| DB 스키마 정의서 | ❌ **마이그레이션 파일 없음.** PostgreSQL DDL 초안이 보고서 §2-5 본문에 있으나 실행된 적 없음 |
| 웹 프레임워크 | ❌ **선택되지 않음** |
| 데이터베이스 인스턴스 | ❌ **프로비저닝되지 않음** |

**따라서 "이 프로젝트가 쓰는 프레임워크는 X입니다" 같은 서술은 이 문서에 없습니다.**
그건 브리핑이 아니라 창작이 됩니다. 대신 이렇게 나눕니다:

- 🔒 **확정** — 설계 문서가 근거와 함께 정한 것. 뒤집으려면 근거를 깨야 함
- 🟡 **미정** — 아직 리더의 결정이 필요한 것. 제 추천과 이유를 붙임
- ⚠️ **함정** — 나중에 비싸게 무는 것. 지금 알아둬야 지시가 정확해짐

> 코드가 0줄이라는 건 나쁜 소식이 아닙니다. **가장 비싼 실수들이 아직 일어나지 않았다**는
> 뜻이고, 이 브리핑의 ⚠️ 항목들이 정확히 그 실수 목록입니다.

## 1. 핵심 아키텍처 및 프레임워크 개념 (Core Concepts)

### 1-1. 🟡 웹 프레임워크 — 미정. 추천은 **FastAPI**

| 후보 | 판정 |
|---|---|
| **★ FastAPI** (Python) | ✅ **추천.** 이유 아래 |
| Django | ❌ 강점이 **ORM + Admin**인데, 이 프로젝트의 주력 저장소는 **DynamoDB**라 ORM이 닿지 않습니다. 무게 대비 이득이 적습니다 |
| Express / NestJS (Node) | 🔶 가능하나 팀의 기존 자산(팀 연구 전체가 Python)과 언어가 갈립니다 |
| Spring Boot (Java) | 🔶 견고하지만 Lambda 콜드 스타트가 불리하고, 팀 역량과 멉니다 |

**FastAPI를 추천하는 이유는 "요즘 빠르다"가 아니라 이 프로젝트의 구조적 이유 셋입니다.**

1. **`pydantic`이 계약 검증기가 됩니다.** 이 프로젝트의 핵심 자산은 `edge_contract.json`
   같은 **계약**입니다. pydantic 모델로 그대로 옮기면 "값이 계약을 벗어나면 요청이 거부된다"를
   코드가 아니라 **타입**으로 강제할 수 있습니다.
2. **OpenAPI 명세가 코드에서 자동 생성됩니다.** 차량 펌웨어 팀과 API 계약을 맞춰야 하는데,
   손으로 관리하는 명세는 반드시 코드와 갈라집니다 — 팀 연구가 문서/코드 괴리로 겪은 바로 그 사고입니다.
3. **Lambda와 Fargate 양쪽에 같은 코드로 배포됩니다** (`Mangum` 어댑터). 아래 1-2의
   "두 런타임을 섞어 쓴다"는 결정과 맞물립니다.

### 1-2. 🔒 확정 — 런타임을 **두 종류로 나눈다**

설계는 서비스를 4개로 가르고, 각각 다른 런타임에 올립니다. 기준은 **호출 패턴**입니다.

| 서비스 | 런타임 | 왜 |
|---|---|---|
| `ingest-reconciler` | **Lambda** | 이벤트가 올 때만 돈다. 차량 업로드는 **폭발적이고 불규칙** |
| `curation-index` | **ECS Fargate** | 질의가 길고(수 초~분) 상시 대기가 필요 |
| `fleet-registry` | **ECS Fargate** | DB 커넥션을 오래 쥔다 (아래 ⚠️ 참조) |
| `mlops-orchestrator` | **Lambda + Step Functions** | 몇 시간짜리 워크플로를 **기다리지 않고** 조율 |

> **비유 — 택시 vs 렌터카.**
> **Lambda**는 택시입니다. 탈 때만 돈을 내고, 안 쓰면 0원입니다. 대신 매번 차를 불러야 하고
> (**콜드 스타트**), 트렁크에 짐을 두고 내릴 수 없습니다(**무상태**).
> **Fargate**는 렌터카입니다. 세워둬도 요금이 나가지만, 시동이 걸린 채 대기하고
> 짐(커넥션 풀·캐시)을 실어둘 수 있습니다.
>
> 하루 두 번 타면 택시가 싸고, 온종일 돌아다니면 렌터카가 쌉니다. **이 프로젝트가 둘 다
> 쓰는 이유는 두 종류의 이동이 다 있기 때문입니다.**

### 1-3. 동기 / 비동기 — 이 프로젝트에서 왜 중요한가

`ingest-reconciler`가 한 건 처리할 때 실제로 하는 일:

```
DynamoDB 읽기  →  S3 메타 조회  →  DynamoDB 조건부 쓰기  →  메트릭 방출
   ~10 ms          ~20 ms              ~10 ms                ~5 ms
```

**연산은 거의 0이고 전부 남을 기다리는 시간(I/O 바운드)입니다.** 동기로 짜면 한 건이
45 ms 동안 프로세스를 통째로 점유합니다. 비동기(`async`/`await`)로 짜면 기다리는 동안
다른 건을 처리합니다.

> **비유 — 식당 종업원.**
> **동기**는 주문을 받고 **주방 앞에 서서 음식이 나올 때까지 기다렸다가** 서빙한 뒤
> 다음 손님을 받는 종업원입니다. **비동기**는 주문을 넣어두고 다른 테이블을 받으러 가는
> 종업원입니다. 요리 속도는 같지만 **홀이 도는 속도가 다릅니다.**
>
> ⚠️ 중요한 오해: **비동기는 CPU를 빠르게 만들지 않습니다.** 이미지 리사이즈나
> 해시 계산처럼 **실제로 CPU를 쓰는 작업**을 `async` 함수 안에 넣으면 이벤트 루프가
> 통째로 멈춰서 **오히려 전체가 느려집니다.** 그런 작업은 별도 워커로 빼야 합니다.

### 1-4. ⚠️ 멱등성(Idempotency) — 이 프로젝트에서는 선택이 아니라 필수

차량은 셀룰러로 붙습니다. **재접속 후 재전송은 가능성이 아니라 확실성입니다.**
같은 프레임 판정이 두 번, 세 번 도착합니다.

> **비유 — 엘리베이터 버튼.**
> 열 번 눌러도 엘리베이터는 한 번만 옵니다. 그게 멱등입니다.
> 반대로 "현재 층에서 한 층 올라가라"는 열 번 누르면 열 층 올라갑니다 — 멱등이 아닙니다.

설계가 이걸 푸는 방법:

```
frame_uuid = SHA256( vin ‖ boot_id ‖ drive_session_id ‖ frame_id )[:16]
             → 같은 프레임은 몇 번 와도 같은 키
             → DynamoDB 조건부 쓰기 attribute_not_exists(PK) 로 중복 흡수
```

**API에도 같은 규율을 적용합니다.** 보고서 §2-2가 변경 요청에 `Idempotency-Key` 헤더를
요구하는 이유입니다 — OTA 배포 버튼을 두 번 누르는 사고는 실제로 일어납니다.

### 1-5. ORM — 작동 방식과, **이 프로젝트에서의 제한된 역할**

**ORM**(Object-Relational Mapping)은 SQL 테이블의 행을 프로그래밍 언어의 객체로 바꿔주는
번역 계층입니다.

> **비유 — 통역사.**
> 여러분은 한국어로 "이 데이터셋에 속한 프레임 다 줘"라고 말하고,
> 통역사가 `SELECT * FROM dataset_frame WHERE ds_id = ...`로 옮깁니다.
> 편하지만 **통역사는 여러분이 무엇을 의도했는지 모릅니다.** 그래서 가끔 끔찍하게
> 비효율적인 문장으로 옮깁니다 — 그게 아래 **N+1 문제**입니다.

```python
# N+1 문제 — 겉보기엔 한 줄이지만 쿼리가 1 + N 번 나간다
for run in session.query(ModelRun).all():        # 쿼리 1번
    print(run.dataset.manifest_s3_uri)           # 루프마다 쿼리 1번씩 → N번
```

**★ 이 프로젝트에서 반드시 알아야 할 것: ORM은 Aurora PostgreSQL에만 닿습니다.**

| 저장소 | ORM | 접근 방법 |
|---|---|---|
| Aurora PostgreSQL | ✅ SQLAlchemy 등 | 테이블·조인·트랜잭션 |
| **DynamoDB** | ❌ **ORM 개념이 성립 안 함** | `boto3` 직접. 접근 패턴이 곧 스키마 |
| S3 | ❌ | `boto3` 객체 키 |
| Athena | ❌ | SQL이지만 **비동기 작업 제출** |

DynamoDB에 ORM을 씌우려는 시도(및 그런 라이브러리)가 있지만, **그건 관계형 사고를
비관계형 저장소에 밀어넣는 것**이고 §2에서 설명할 키 설계를 망칩니다.
**지시하실 때 "ORM으로 처리해줘"가 통하는 범위는 Aurora뿐입니다.**

### 1-6. 🔒 이벤트 구동 + 최종 일관성 — 13.62시간의 스큐

이 프로젝트에서 가장 낯선 개념이자, 백엔드 설계를 통째로 규정하는 것입니다.

```
판정 메타데이터 (12 B)  ──  MQTT  ──▶  수 초 안에 도착
원본 이미지 (144.5 KB)  ──  S3   ──▶  최대 13.62 시간 뒤 도착 (또는 영영 안 옴)
```

**두 조각이 최대 13.62시간 어긋나 도착합니다.** 일반적인 웹 서비스라면 "요청 하나 =
데이터 하나"지만, 여기서는 **한 프레임의 정보가 두 번에 나눠 도착하고 그 사이 간격이 반나절**입니다.

> **비유 — 우편함.**
> 친구가 "선물 보냈어"라고 카톡을 먼저 보내고(판정), 택배는 반나절 뒤 도착합니다(페이로드).
> 카톡만 온 상태는 **오류가 아니라 정상**입니다. 여기서 "택배가 없으니 뭔가 잘못됐다"고
> 알람을 울리면 운영이 마비됩니다.

그래서 설계는 **`PENDING`을 정상 상태로** 모델링합니다.

```
PENDING ──(S3 Event)──▶ UPLOADED ──▶ INDEXED ──▶ LABELED ──▶ IN_DATASET
   └────(TTL 만료 / 드롭 보고)────▶ DROPPED
```

**최종 일관성**(eventual consistency)이란 "지금 당장은 안 맞아도 결국은 맞는다"입니다.
강한 일관성(항상 맞음)을 쓰려면 느리고 비싸지므로, **틀려도 되는 곳에서는 안 씁니다.**
이 프로젝트가 프레임 인덱스는 DynamoDB(최종 일관성), 캠페인·배포는 Aurora(강한 일관성)로
가른 기준이 정확히 이것입니다.

## 2. 데이터베이스 및 스키마 구조의 이해 (Database Engineering)

### 2-1. 🔒 확정 — 저장소를 4개로 나눈다. **기준은 일관성 요구**

"DB 하나 고르기"가 아니라 **데이터의 성격별로 다른 저장소를 쓰는 것**을
**폴리글랏 퍼시스턴스**(polyglot persistence)라 합니다. 이 프로젝트는 4계층입니다.

| 계층 | 저장소 | 담는 것 | 틀리면? |
|---|---|---|---|
| ① 객체 | **S3** | 이미지·모델 가중치·데이터셋 매니페스트 | 프레임 한 장 유실 — 무해 |
| ② 핫 인덱스 | **DynamoDB** | 활성 상태 프레임 판정 | 한 건 틀려도 통계적으로 무해 |
| ③ 트랜잭션 | **Aurora PostgreSQL** | 캠페인·데이터셋 버전·모델 런·배포 | ❗ **함대에 잘못된 설정이 나간다** |
| ④ 분석 | **S3 + Glue + Athena** (Parquet) | 판정 전량 이력 | 재계산 가능 |

> **한 줄로: 일관성 요구가 저장소를 고릅니다.**
> "캠페인 C를 차량군 G에 배포했다"는 **틀리면 안 되는 사실**이라 외래키·트랜잭션이 필요합니다.
> "프레임 #1048322의 conf_q8이 43이었다"는 14억 건 중 하나라 한 건 틀려도 아무 일 없습니다.

### 2-2. Aurora PostgreSQL — ERD

```mermaid
erDiagram
  campaign {
    text    campaign_id PK
    jsonb   profile_json
    char16  profile_sha UK "DynamoDB 와의 조인키"
    numeric select_rate
    bool    parity_verified "FALSE 면 배포 불가 (CHECK)"
  }
  dataset_version {
    text ds_id PK
    text manifest_s3_uri
    int  n_frames
    int  split_seed
    text parent_ds_id FK "증분 계보 (자기참조)"
  }
  dataset_frame {
    text ds_id PK_FK
    char16 frame_uuid PK "DynamoDB 로의 논리적 참조"
    text split "tune | pool | held_out"
  }
  model_run {
    text run_id PK
    text ds_id FK
    text base_run_id FK "자기참조"
    int  epochs
    int  seed
    text optimizer "CHECK optimizer <> 'auto'"
  }
  eval_result {
    text   run_id PK_FK
    text   metric PK
    float  value
    text   baseline_run FK
    float  ci_low "비열등성 게이트 입력"
  }
  deployment {
    text deployment_id PK
    text kind "weights | profile | firmware"
    text campaign_id FK
    text run_id FK
    text stage "canary | staged | fleet | rolled_back"
  }

  dataset_version ||--o{ dataset_frame : "포함한다"
  dataset_version ||--o{ model_run     : "학습에 쓰인다"
  dataset_version ||--o{ dataset_version : "파생된다"
  model_run       ||--o{ eval_result    : "평가된다"
  model_run       ||--o{ model_run      : "이어서 학습된다"
  model_run       ||--o{ deployment     : "가중치로 배포된다"
  campaign        ||--o{ deployment     : "프로파일로 배포된다"
```

**이 ERD가 답하려는 질문은 단 하나입니다 — "이 mAP 숫자가 어느 데이터에서 어느 가중치로
나왔는가."** 조인 한 번에 나와야 합니다. 지금 이 계보는 `NeedSlack/실험추적_rev10.xlsx`,
즉 **엑셀 시트**에 있습니다. 그걸 관계 스키마로 승격하는 것이 이 테이블들의 존재 이유입니다.

### 2-3. DynamoDB — ⚠️ **ERD가 없습니다. 그게 정상입니다**

| | 관계형 (Aurora) | DynamoDB |
|---|---|---|
| 설계 순서 | 데이터를 정규화 → 나중에 질의 | **질의를 먼저 정한다** → 그에 맞춰 키 설계 |
| 새 질의 추가 | `WHERE` 절만 바꾸면 됨 | **GSI를 새로 만들거나 못 함** |
| 조인 | `JOIN` | **없음.** 애플리케이션이 두 번 읽음 |
| 테이블 수 | 개념당 하나 | **단일 테이블에 전부** (`ns-curation-index`) |

> ★ **DynamoDB에서 스키마는 곧 접근 패턴입니다.** 그래서 "테이블 설계해줘"가 아니라
> **"이런 질의를 해야 한다"**고 지시하셔야 합니다. 질의를 안 알려주고 만든 키 설계는
> 반드시 나중에 못 쓰게 됩니다.

설계가 이미 고정한 접근 패턴 5개:

| 질의 | 키 |
|---|---|
| 프레임 단건 조회 | `PK = FRAME#{uuid}` |
| 차량의 최근 판정 시계열 | `PK = VEH#{vin}#{날짜}`, `SK = TS#...` |
| 상태별 지연 감시 | GSI1 `STATE#{상태}#{shard}` |
| 고득점 마이닝 | GSI2 `CMP#{campaign}#B{점수버킷}` |
| 캠페인 진척 | GSI1 `CMP#{campaign}` |

### 2-4. ⚠️ 병목과 무결성 — 확장·수정할 때 무는 것 6가지

#### ⚠️ ① 단일 RDBMS는 이 쓰기율에서 깨진다 — 숫자로

```
10만대 · 2 h/일 · 20 Hz · rate 0.10
  → 선별 프레임 1.44 G rows/일 = 평균 16,667 rows/s (피크는 그 수 배)
```

Aurora 단일 라이터는 이 쓰기율을 감당하지 못합니다(수만 IOPS 벽). 샤딩하면 조인과
트랜잭션을 잃는데, **그건 RDBMS를 쓰는 유일한 이유를 포기하는 것**입니다.
→ 그래서 프레임 인덱스는 DynamoDB로 갑니다. **"전부 PostgreSQL에 넣자"고 지시하시면
이 벽에 부딪힙니다.**

#### ⚠️ ② DynamoDB를 아카이브로 쓰면 비싸진다

| | 쓰기/일 | 온디맨드 쓰기 비용 |
|---|---|---|
| 선별 프레임 전량 | 14.4억 | **$54,000/월** |
| 후보 전량 로깅 시 | 144억 | $540,000/월 |

→ 설계의 답: **"지금 뭔가를 기다리고 있는" 프레임만** DynamoDB에 두고, `TTL 30일`로
자동 만료시켜 Streams → Firehose → **Parquet**으로 내립니다. 이 수명주기 하나로
저장 비용이 **선형 증가에서 상수로** 바뀝니다.

#### ⚠️ ③ 핫 파티션 — `STATE#PENDING`은 그대로 쓰면 터진다

전 함대의 프레임이 한 값에 몰립니다. DynamoDB는 파티션 키로 데이터를 분산하는데,
모두가 같은 키를 쓰면 **한 파티션이 전체 트래픽을 받습니다.**
→ 16-way 샤드 접미사(`STATE#PENDING#07`) 후 병렬 스캔. **새 GSI를 추가하실 때마다
"이 키에 값이 몰리지 않나?"를 물으셔야 합니다.**

#### ⚠️ ④ 정렬키는 **사전식**이다 — 숫자가 숫자로 안 정렬된다

```
잘못:  "231" < "99"   ← 사전식이라 참이 된다
바름:  "00231" < "00099" 로 제로패딩 → 수치 정렬 복원
```
점수·카운트를 정렬키에 넣을 때 **반드시** 고정 폭 제로패딩. 나중에 발견하면 전체 재색인입니다.

#### ⚠️ ⑤ 외래키가 없는 경계 — 애플리케이션이 지켜야 한다

```
DynamoDB.profile_sha  ──?──  Aurora.campaign.profile_sha
DynamoDB.frame_uuid   ──?──  Aurora.dataset_frame.frame_uuid
```

**두 저장소 사이에는 외래키가 없습니다.** DB가 막아주지 않으므로, 존재하지 않는 캠페인을
가리키는 프레임이 생길 수 있습니다. → 쓰기 경로에서 검증하고, **정합성 배치 작업**을
주기적으로 돌려야 합니다. 지시하실 때 이 경계를 의식하셔야 합니다.

#### ⚠️ ⑥ 🔴 가장 비싼 함정 — **차량 펌웨어는 롤아웃이 수 주다**

일반 웹 서비스는 스키마를 바꾸고 클라이언트를 같이 배포하면 끝입니다.
**여기서는 구버전 차량이 몇 주 동안 계속 옛 형식으로 보냅니다.**

| 변경 | 안전? |
|---|---|
| 필드 **추가** (optional, 기본값 있음) | ✅ 안전 |
| 필드 **삭제** | ❌ 구버전이 계속 보냄 |
| 필드 **의미 변경** | ❌❌ **최악.** 두 의미가 한 컬럼에 섞이고 사후 구별 불가 |
| protobuf **필드 번호 재사용** | ❌❌ 구버전이 새 필드를 옛 타입으로 해석 |
| 필수 필드 **추가** | ❌ 구버전 메시지가 전부 거부됨 |

→ **규칙: 추가만 하고, 지우지 말고, 번호를 재사용하지 말 것.** 그리고 모든 레코드에
**스키마 버전을 실을 것.**

## 3. 핵심 성능 및 안정성 지표 (Key Metrics)

### 3-1. ⚠️ 먼저 — **평균을 보지 마세요**

```
응답시간 100건: 99건이 10 ms, 1건이 10,000 ms
  평균 = 109 ms    ← "빠르네"
  p99  = 10,000 ms ← 100명 중 1명은 10초를 기다렸다
```

**평균은 최악을 숨깁니다.** 백분위수(percentile)로 보셔야 합니다.

| 표기 | 의미 |
|---|---|
| **p50** (중앙값) | 절반이 이보다 빠르다 — "보통 경험" |
| **p95 / p99** | 상위 5% / 1%의 느린 경험 — **여기가 진짜 사용자 불만** |
| p99.9 | 함대 규모에서는 이것도 매일 수천 명 |

### 3-2. 일반 백엔드 지표

| 지표 | 무엇 | 이 프로젝트의 초기 목표 |
|---|---|---|
| **Latency** (p50/p99) | 요청 → 응답 | 조회 API p99 < 300 ms |
| **TPS / RPS** | 초당 처리 건수 | 수집 평균 16,667 판정/s (10만대) |
| **Error rate** | 5xx 비율 | < 0.1% |
| **Saturation** | 자원 포화도 | CPU·메모리·**커넥션 풀** |
| **DB 쿼리 실행시간** | 느린 쿼리 | p99 < 100 ms, `pg_stat_statements`로 추적 |
| **DynamoDB throttle** | 용량 초과 거부 | **0 이어야 함.** 0이 아니면 핫 파티션 신호 |
| **Athena 스캔 바이트** | 질의당 스캔량 | 비용 직결 ($5/TB). 파티션 프루닝이 되는지의 지표 |

> ⚠️ **커넥션 풀 포화**는 Lambda에서 특히 위험합니다. Lambda는 동시 실행이 수백 개로
> 순식간에 늘어나는데 각자 DB 커넥션을 열면 **PostgreSQL이 먼저 죽습니다.**
> → **RDS Proxy**를 반드시 끼우거나, DB에 닿는 경로는 Fargate로 몰아야 합니다.
> (설계가 `fleet-registry`를 Fargate에 둔 이유 중 하나입니다.)

### 3-3. ★ 이 프로젝트에만 있는 지표 — 여기가 진짜 중요합니다

일반 백엔드 대시보드에는 없지만, **이게 없으면 시스템이 망가져도 모릅니다.**

| 지표 | 정의 | 임계 | 넘으면 무슨 뜻인가 |
|---|---|---|---|
| **ArrivalLatencySeconds** p99 | `t_ingest − t_frame` | **< 49,030 s** (13.62 h) | 유도한 `L_max` 명세 위반. 주행 듀티가 `δ_max`(43.3%)를 넘었거나 링크가 가정보다 나쁘다 |
| **드롭률** | 드롭 / 선별 | 모델 예측과 대조 | 갈리면 `UPLINK_BPS = 1 Mbps` 가정이 틀렸다는 신호 |
| **PENDING 적체** | 20 h 초과 `PENDING` 수 | 0에 수렴 | 페이로드 경로가 막혔다 |
| **Reconcile 성공률** | `UPLOADED` / `PENDING` | — | 판정↔페이로드 짝짓기 건전성 |
| **차량별 큐 점유** | ⑦ NVMe 사용량 | < 6.13 GB | `Q_min` 초과 = 모델 밖 운용 |
| **기전별 분포** | `reclaim_mode` 비율 | 추적만 | 모집단 혼재 감시 (설계결정-0001) |

> **`L_max` 13.62 h는 유도된 값이지 관측된 값이 아닙니다.** 실측으로 감시해야 비로소
> 명세가 됩니다. 이 지표 하나가 설계 전체의 검산입니다.

### 3-4. SLI / SLO / 에러 버짓 — 용어 정리

- **SLI** (Indicator): 측정하는 값. "조회 API p99 지연"
- **SLO** (Objective): 목표. "p99 < 300 ms를 30일간 99.9%"
- **에러 버짓**: 허용된 실패량. 99.9%면 30일에 **43분**.

> **에러 버짓이 리더에게 주는 것은 "속도를 낼지 안정을 택할지"의 객관적 근거입니다.**
> 버짓이 남으면 공격적으로 배포하고, 다 쓰면 기능 대신 안정화에 돌립니다.
> "느낌"이 아니라 숫자로 결정됩니다.

## 4. 향후 작업을 위한 '프롬프트 지시 가이드'

### 가이드 1 — **계약을 먼저 고정해서 지시하세요**

AI가 가장 많이 틀리는 지점은 로직이 아니라 **여러분이 말하지 않은 부분을 추측한 곳**입니다.

| ❌ 이렇게 말하면 | ✅ 이렇게 |
|---|---|
| "프레임 조회 API 하나 만들어줘" | "`GET /v1/frames/{frame_uuid}`. **응답**: 판정 메타 전체 + S3 presigned URL(TTL 15분). **404**: 존재하지 않는 uuid. **410**: `DROPPED` 상태. **403**: 다른 테넌트. presigned URL은 `state≥UPLOADED`일 때만 포함." |

지시에 반드시 넣을 것: **요청/응답 페이로드 형태 · 상태 코드별 조건 · 인증 주체 ·
멱등성 필요 여부 · 페이지네이션 방식**.

> 특히 **예외 기준**입니다. "없으면 어떻게 할까"를 안 알려주면 AI는 그럴듯한 쪽을
> 고르는데, 이 프로젝트에서는 `PENDING`이 정상이라 **"없음"과 "아직 안 옴"이 다릅니다.**

### 가이드 2 — **규모와 접근 패턴을 숫자로 주세요**

"빠르게" "효율적으로"는 지시가 아닙니다. 같은 코드가 1,000건에서는 맞고 14억 건에서는 틀립니다.

| ❌ | ✅ |
|---|---|
| "프레임 조회 빠르게 해줘" | "차량 1대의 **최근 24시간** 판정을 시간 역순으로. 하루 **17만 건**, 페이지 100건, **p99 < 300 ms**." |
| "테이블 설계해줘" | "이 **5가지 질의**를 해야 한다: ① … ② … 이 접근 패턴으로 키를 설계해줘." |

**DynamoDB는 접근 패턴이 곧 스키마입니다**(§2-3). 질의를 안 주면 반드시 다시 만들게 됩니다.

> 그리고 **수치는 `schema/edge_contract.json`에서 인용하세요.** 기억이나 대화에서 끌어오면
> 값이 갈라집니다 — 팀 연구가 비싸게 배운 교훈이고, 그래서 계약을 스냅샷으로 굳혔습니다.

### 가이드 3 — **되돌릴 수 있는지 명시하세요**

이 시스템에는 **되돌리기 어려운 작업**이 섞여 있습니다. AI는 지시받은 일만 하고
롤백 경로는 **말하지 않으면 만들지 않습니다.**

| 작업 | 되돌리기 |
|---|---|
| API 코드 수정 | ✅ 쉬움 |
| DB 마이그레이션 | ⚠️ **되돌리는 마이그레이션을 같이 요구해야 함** |
| S3 수명주기 정책 | ⚠️ 이미 삭제된 객체는 안 돌아옴 |
| **차량 OTA 배포** | 🔴 **함대에 나감.** canary → 단계 확대 → 자동 중단 기준이 함께 있어야 함 |
| DynamoDB 키 스키마 변경 | 🔴 **전체 재색인**. 사실상 불가 |

```
❌ "campaign 테이블에 tile_mode 컬럼 추가해줘"
✅ "campaign 에 tile_mode BOOLEAN NOT NULL DEFAULT FALSE 추가.
    up/down 양방향 마이그레이션, 무중단(기본값 있는 nullable → 백필 → NOT NULL 3단계),
    기존 행 영향 없음을 확인하는 검증 쿼리까지."
```

> 지시에 **"이 작업의 롤백 경로도 같이 제시해줘"** 한 줄을 붙이는 습관이,
> 이 프로젝트에서 가장 값싼 보험입니다.

### (보너스) 가이드 4 — **모르면 모른다고 하라고 지시하세요**

이 브리핑이 §0에서 한 일이 그것입니다. 존재하지 않는 프레임워크를 "이 프로젝트는 FastAPI를
씁니다"라고 답했다면 이후 모든 지시가 틀어졌을 겁니다.

> 지시 끝에 붙이면 좋은 문장:
> **"확실하지 않거나 파일에서 확인되지 않은 건 추측하지 말고 모른다고 하고, 근거 파일 경로를 같이 달아줘."**
